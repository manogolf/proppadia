## Prepared SQL and safeguards

The SQL is generated by `backend/nhl/scripts/prepare_nhl_2025_attempts_repair.py` from the fixed-hash candidate and the fixed-hash fresh snapshot:

- `backend/nhl/sql/repairs/repair_nhl_2025_shot_attempts_from_official_pbp.sql` — SHA-256 `013e991cfc35df3cba80560e3664606c084e7c0942ed826481549975daa24993`.
- `backend/nhl/sql/repairs/rollback_nhl_2025_shot_attempts_from_official_pbp.sql` — SHA-256 `49552f8f7b397b48d0c0ea9f7e4919f1811221708a21c44f4d6d07a7225f75fa`.

Both scripts carry 34,108 exact keys, original attempt values, official counts, and per-game PBP and boxscore hashes. They are explicitly marked **prepared only**. They constrain keys to the `202502` range, require every target and unresolved row to exist, compare current unresolved values with their read-only snapshot, and abort on any target value other than the complete original state or complete corrected state. Partial application or unexpected values abort the transaction. The forward script updates only `shot_attempts`; the allowed changed-row count is either 34,108 on first application or zero on a fully corrected retry. It asserts every target equals the official value after the update and that all 6,368 unresolved values remain unchanged. Rollback requires the complete corrected or complete original state and restores only the original attempt values; it is also idempotent. Both emit key-level before/after attempt rows after commit for retention by the authorized operator. No rollback was run.

The correction is ready for separate execution authorization. An authorized execution should retain the current snapshot, the psql row-level output, a post-update export, and a transaction receipt together; none of those post-update artifacts exists yet because no write was authorized here.
